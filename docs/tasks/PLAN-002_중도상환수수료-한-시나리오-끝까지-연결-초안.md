## 1. 끝까지 연결할 한 시나리오

합성 기업 `SW-COMPANY-001`(가상상사)이 셀러론 상담 신청 `SW-APPLICATION-001`을 냈다. 행원이 2026-10-06에 상담을 준비한다. 적용 공문은 중도상환수수료 v2(0.8퍼센트, 2026-10-01 시행), 승인 checklist는 TASK-007로 발행된 것이다.

1. 행원(또는 AI 서비스)이 "이 신청 건의 상담 준비안"을 요청한다.
2. AI 서비스가 Core Tool 1로 적용 checklist를 읽는다. 사용 가능하면 준비안을 만들고, 사용 불가면 **보류**(사유 그대로 전달, 수기 checklist 안내).
3. 행원이 "중도상환수수료 예외"처럼 질문하면 근거를 검색한다. 검색 결과는 후보일 뿐이고, **각 후보를 Core Tool 2로 다시 확인**해 사용 불가·다른 공문군·미승인 근거는 제외한다.
4. 행원이 준비안과 근거를 보고 최종 확인을 기록한다. 기록은 Core에 남는다.
5. AI 서비스가 꺼져 있으면 화면은 Core의 수기 checklist를 그대로 보여 준다(MVP 9단계).

### TASK-014 검색 골든셋과 평가 기준 (검색 구현 전)

상세 계획은 [TASK-014](TASK-014_검색-골든셋과-평가-기준.md)(PR #34, 검토 중)에 있다. 아래 요약과 상세 계획이 다르면 상세 계획을 따른다. 상세 계획 작성은 승인됐고, **골든셋 작성 착수, 검색 구현, 지표 수치 확정은 각각 별도 판단**이다(초기 점검용 10건과 정답·보류 이유를 사용자가 확인한 뒤 착수 여부를 정한다).

- 골든셋은 두 묶음으로 나눈다. **초기 점검용 10건**(`…-smoke-v1.json`, 구현 중 빠른 확인)과 **최종 평가용 20~30건**(`…-eval-v1.json`, 기준선과 최종 구성 비교·통과 판정). 초기 점검용 질의는 최종 평가용에 넣지 않는다. 위치 `datasets/synthetic/search-goldenset/`. 질의마다 `query`, `family_id`(요청 범위), `business_date`, `relevant`(사용 가능해야 하는 규칙 version ID 목록), `must_not`(사용 불가·구버전·요청 범위 밖 규칙 version ID 목록), `expected_evidence_hold`(근거 보류), `requires_human_decision`(처리 판단 보류, 기록용), `expected_fields`(최종 근거에 포함돼야 하는 구조화 값), `category`, 작성 근거. 파일 머리에 `dataset_class: SYNTHETIC_WORK`, `goldenset_version`, `evaluation_context`(평가 시각, 승인 상태, 자료 해시를 고정해 정답이 날짜나 로컬 DB 상태에 따라 바뀌지 않게 함). 버전 번호를 붙여 바꾸면 새 버전으로 기록한다.
- 두 가지 보류를 구분한다. **근거 보류**(`expected_evidence_hold`)는 재확인 뒤 제공할 근거가 없어 목록이 비는 것이며 검색 필터와 Core 재확인이 만든다. **처리 판단 보류**(`requires_human_decision`)는 근거는 보여 주되 "이 고객을 이렇게 처리해도 되는가"를 사람에게 남기는 것이며 준비안 단계(TASK-015)와 사람 확인(TASK-017)이 담당한다. 골든셋 지표는 근거 보류만 잰다.
- 질의 범주(상세 계획 기준): `direct`, `paraphrase`, `numeric`, `old_value_apply`(구버전 값을 현재 업무에 적용하려는 질문: 구버전 근거는 `must_not`, **현재 근거는 `relevant`로 제공**, 처리 판단은 사람), `current_value`(값이 바뀌었는지, 지금 얼마인지: 최신 사용 가능 근거 제공), `other_family`(요청 범위 밖 공문군: 근거 보류), `unapproved`(요청 범위 안 미승인 규칙: 근거 보류), `decision_forbidden`(승인 여부를 AI에게 묻는 질문: 근거 보류, AI는 결정하지 않음), `hold`(관련 근거 없음), `before_approval`(승인 전 업무일 조회: 근거 보류). 역사적 비교 조회("전에는 얼마였고 지금은 얼마인가")는 범위 밖이다.
- 지표(제안, 확인 뒤 확정): 최종 사용자 응답 기준으로 Recall@5, MRR, **미승인·사용 불가·요청 범위 밖 근거 노출률 0건(필수)**, 잘못된 보류(답할 수 있는 질문을 보류한 비율)와 놓친 보류(보류해야 하는 질문에 근거를 제공한 비율, 0% 필수), 필드 제공 지표, 질의당 Core 재확인 호출 수. 후보 단계에서는 metadata 제외 조건 준수를 따로 측정하고 재확인으로 제거된 후보 수와 이유를 기록한다. 최종 노출 0건만으로 검색 필터가 올바르다고 판단하지 않는다.
- 통과 기준(**제안값, 미확정**): BM25 기준선 Recall@5 ≥ 0.8, MRR ≥ 0.7, 노출률 0, 놓친 보류 0%. 최종(TASK-018) 목표: Recall@5 ≥ 0.9, MRR ≥ 0.8, 노출률 0. 수치는 TASK-014에서 질문, 정답 근거, 보류 사례, 계산 방법을 사용자가 확인한 뒤 확정한다. 기준선이 확정값을 못 넘으면 검색 구현을 시작하지 않고 골든셋과 색인 설계를 다시 본다.
- 평가 방법: 평가 스크립트 명세(입력 골든셋, 검색 API 호출, Core 확인 뒤 결과, 지표 계산, `evaluation_context`가 실제 환경과 다르면 평가 거부, 결과 파일 `docs/evidence/SEARCH_EVALUATION_<버전>.md`). 구현은 TASK-016. 같은 골든셋으로 BM25와 최종 구성을 비교한다.
- 완료 확인 조건: 상세 계획의 AC-01~08을 따른다(골든셋 schema 통과, 모든 규칙 version ID가 실제 합성 공문에 존재, 구버전·요청 범위 밖·미승인 항목이 `must_not`에 있음, 근거 보류 범주별 1건 이상, `old_value_apply`는 현재 근거를 `relevant`로 가짐, 두 단계 지표와 통과 기준이 판단 기록으로 확정, `evaluation_context` 필수).

### TASK-011a Core 전체 흐름 연결 검증 (화면 전, 완료)

**완료**(결정자 사용자. 계획·판단·검수 기록 PR #35, 구현 PR #36). 상세는 [TASK-011a](TASK-011a_Core-전체-흐름-연결-검증.md)와 evidence `docs/evidence/CORE_END_TO_END_FLOW_EVIDENCE.md`. 완료 범위는 화면 전 Core 전체 흐름 연결 검증이며, 검색·AI 서비스·화면·실제 사용자 권한의 완료가 아니다. 확정한 동작: 거부된 요청은 실패 이유를 실행 기록에 남기고 사람 결정, 승인 checklist, 적용 일정을 만들지 않는다. 실패 조회 화면, 재처리, 자동 재시도는 범위 밖이다. 아래는 계획 당시 기록이다.

- 이미 자동 검증으로 충족한 범위(기존 테스트 기준, 사실): 격리 DB에서 합성 공문 적재 → 예시 checklist → 변경안 생성 → 자동 검증 → 승인·수정·반려 → 발행(`HumanReviewIntegrationTest`), 같은 흐름 뒤 HTTP 적용 공문 조회와 사용 허용·차단(`HumanReviewApplicableIntegrationTest`), 같은 흐름 뒤 Tool 조회와 근거(`ToolApiIntegrationTest`). 세 클래스 모두 서비스 객체를 테스트가 직접 만들어 호출한다.
- 부족한 연결(사실): (1) **demo 명령 진입점**(`ProposalDemoConfiguration`의 ApplicationRunner 4개: 예시 적재, 변경안 생성, 검증, 사람 결정)을 통해 흐름을 타는 테스트가 없다. 설정 키·필수 인자·runner 조합은 README 설명만 있다. (2) 수정(MODIFY) → 재검증 → 승인 뒤 **조회와 Tool 응답**까지 이어지는 테스트가 없다(승인까지만 있다). (3) 한 흐름을 처음부터 끝까지 한 문서로 재현하는 evidence가 없다.
- 범위: 위 세 가지만 추가한다. 기존 테스트는 재작성하지 않는다. 새 테스트 1클래스(runner 설정으로 Spring 컨텍스트를 띄워 S1~S7 순서대로 실행하고 각 단계의 DB 상태와 HTTP 응답을 확인), evidence `docs/evidence/CORE_END_TO_END_FLOW_EVIDENCE.md`(단계별 명령, 입력, 실제 출력).
- 완료 확인 조건 초안: (1) runner 조합으로 적재 → 생성 → 검증 → 승인이 순서대로 실행되고 각 단계 기록이 남는다. (2) 승인 뒤 적용 공문 조회와 Tool 조회가 같은 version·결정 ID를 돌려준다. (3) 수정 → 재검증(WARN) → 사유 승인 → 조회에서 고친 문구가 보인다. (4) 잘못된 순서(검증 전 승인, 미승인 조회)는 각 단계가 거부한다. (5) 기존 테스트 수 유지, evidence에 실제 출력. 사용자별 권한과 화면은 포함하지 않는다.

### TASK-015 AI 서비스 최소 흐름: 규칙 조립 준비안과 보류

- 범위: Python FastAPI 서비스(`apps/ai-service`). 업무 DB 접근 없음, Core Tool만 호출. **LLM 없음: 준비안은 규칙으로 조립한다(첫 연결 단계). LLM 기반 생성·검증은 TASK-019이며 이 Task 완료를 "AI 생성 완료"로 표현하지 않는다.** 준비안 = 신청 건(합성) + 적용 공문 + 승인 checklist 항목 + 항목별 근거 ID. 보류 = `usable=false`면 사유 코드와 사람이 읽을 설명, 수기 checklist 안내 문구.
- Core 쪽 추가(채택): 준비안·보류 기록 테이블(V10, append-only)과 기록용 쓰기 endpoint 1개(**Tool이 아니라 별도 경로**, 같은 서비스 토큰, 기록만 가능). 준비안은 Core가 저장 전에 적용 공문 조회 결과와 다시 대조해 사용 불가 상태면 저장을 거부한다(최종 Core 확인).
- 실행 가능한 흐름: `python -m ai_service prepare --application SW-APPLICATION-001 --business-date 2026-10-06` → 준비안 JSON 또는 보류 JSON, Core에 기록 ID.
- 완료 확인 조건 초안: (1) 승인된 기간은 준비안에 항목 3개와 근거 ID. (2) 미승인 기간은 보류, 사유 `HUMAN_REVIEW_PENDING` 등, 항목 없음. (3) Core 거부: AI가 사용 가능이라고 주장해도 Core가 사용 불가면 기록 거부. (4) Tool 401/403은 보류로 변환(fail-closed). (5) AI 서비스에 DB 자격증명 없음(설정 검사). (6) 감사: Tool 호출 감사와 준비안 기록이 연결됨(상담 ID).

### TASK-016 근거 검색 기준선 + Core 최종 확인

- 색인 대상: 승인 checklist 항목(instruction, structured_change 텍스트화)과 규칙 원문(evidence_text). 문서 metadata: `dataset_class`, `synthetic`, `family_id`, `notice_id`, `rule_version_id`, `approval_status`(승인 checklist 항목의 근거인지), `effective_from/to`. 색인은 Core에서 ES로 보내는 재색인 job(멱등, 두 번 실행 시 문서 수 불변).
- 검색: BM25 + metadata filter(승인 항목 근거만, 공문군 일치). 결과 후보를 **Core Tool 2로 하나씩 재확인**해 통과한 것만 반환. 검색 인덱스는 업무 원장이 아니다(CLAUDE.md).
- 실행 가능한 흐름: `POST /api/v1/ai/search`(AI 서비스) → ES 후보 → Core 확인 → 근거 목록. TASK-014 평가 스크립트로 지표 산출.
- 완료 확인 조건 초안: 골든셋 통과 기준 충족, 노출률 0, 색인 멱등, compose에 ES 추가, 평가 결과 evidence. **dense k-NN과 reranker는 이 Task에서 빼지 않는다. 다음 Task에서 추가하며 이 Task는 기준선 측정이다.**

### TASK-017 행원 최종 확인 기록과 최소 화면

- 화면 1개(상담 준비): 신청 건 선택 → 준비안 또는 보류 사유 → 근거 검색 → 항목별 "근거 확인" 체크 → 최종 확인 기록. AI 서비스가 꺼져 있으면 Core applicable 조회로 수기 checklist를 그대로 표시하고 "AI 준비안 없음"을 알린다.
- Core 쪽: 행원 최종 확인 기록(V11, append-only, 행원 ID는 합성, 근거 ID와 준비안 ID 참조). 승인·거절 결정은 기록하지 않는다(AI와 화면은 여신 결정 주체가 아니다).
- 완료 확인 조건 초안: 화면에서 시나리오 1~5 재현, 보류 상태에서 확인 기록 불가, AI 중단 시 수기 checklist 표시, 기록에 근거 ID 포함.

### TASK-018 검색 최종 범위(dense vector k-NN + reranker)와 ADR-010

- 임베딩은 **로컬 실행을 초기 방향으로 채택**한다. 합성 공문이라도 외부 임베딩 API에 보내지 않는 것은 이 계획의 선택이며, TASK-018 계획에서 후보 모델(한국어 지원), 필요한 장비(CPU/GPU, 메모리), 예상 품질과 색인 시간, 대안(다른 로컬 모델, 외부 API를 쓸 경우의 조건)을 제시하고 다시 판단한다. reranker도 같은 기준으로 제시한다. 단순 Hybrid와 경량 온톨로지 metadata 비교. 최종 평가용 골든셋으로 BM25 기준선과 비교표, 인간 선택 기록. Core 최종 확인은 그대로.
- 완료 확인 조건 초안: 최종 목표 지표 충족 또는 미달 시 대안과 별도 판단, 노출률 0 유지, 응답 시간 기록.

## 6. 판단이 필요한 제안 (상세)

- 제안 1: TASK-015의 준비안은 LLM 없이 규칙으로 조립한다. LLM 문장 생성은 화면(TASK-017) 뒤 별도 Task.
- 제안 2: TASK-015의 준비안 기록은 Tool이 아니라 별도 쓰기 endpoint로 두고 Core가 저장 전 사용 가능 여부를 다시 확인한다(ADR-011 "쓰기 Tool 없음" 유지).
- 제안 3: 골든셋 통과 기준 수치(기준선 Recall@5 0.8/MRR 0.7, 최종 0.9/0.8). 근거가 약하므로 TASK-014에서 질의 수와 함께 확정.
- 제안 4: 임베딩 모델은 로컬 실행 가능한 것으로 제한(외부 API에 합성 공문 전송 금지). TASK-018 시작 전 판단.

**판단** - 이 초안의 분할·방향 승인과 제안 1~4의 판단은 5절에 기록돼 있다(결정자 사용자, PR #32). 각 Task의 구현 착수는 그 Task 시작 전에 별도로 검토·승인한다. 5절의 승인은 후속 구현 전체의 착수 승인이 아니다.
