# TASK-014 검색 골든셋과 평가 기준 (검색 구현 전)

- 상태: **계획 검토 대기** (상세 계획 작성 승인: 사용자. 제안 3건과 추가 조건 5건 반영. 골든셋 작성 착수와 검색 구현은 미승인)
- 담당자 / 인간 결정자: AI 조사·초안·골든셋 작성 / 사용자 질문·정답 근거·보류 사례·계산 방법 확인과 수치 확정
- 요구사항 출처: PLAN-002 TASK-014 절과 사용자 판단(초기 점검용 10건과 최종 평가용 20~30건 구분, Recall@5·MRR 수치는 제안값, 확인 뒤 확정), DEVELOPMENT_RULES "검색은 골든셋 버전, Recall@5/MRR 등 지표와 근거성/보류 기준을 구현 전 정의", CLAUDE.md 검색 baseline(BM25 + dense vector k-NN + metadata filter + reranker)
- 관련 Task: TASK-008(완료, Tool 2개), TASK-016(BM25 기준선, 이 Task 뒤), TASK-018(벡터 + reranker, 최종 평가용 골든셋으로 비교)

## Goal / 관련 요구사항

- Goal: 검색을 구현하기 전에 "무엇을 찾아야 정답이고, 무엇이 나오면 안 되며, 언제 보류해야 하는가"를 데이터와 숫자로 고정한다. 이후 TASK-016(BM25)과 TASK-018(벡터 + reranker)은 같은 골든셋으로 비교한다.
- 입력: 합성 공문 4건(중도상환수수료 v1·v2, 셀러론 v1·v2)의 규칙 version ID(아래 표), TASK-007·008로 확정된 "사용 가능" 상태 규칙(승인된 중도상환수수료 v2 항목 3개), 합성 신청 건.
- 출력: 골든셋 파일 2개, 골든셋 계약 schema, 지표 정의와 계산 방법, 평가 스크립트 명세, 통과 기준 확정 기록. **코드 변경 없음**(평가 스크립트 구현은 TASK-016).
- 사용자: 검색 구현자(AI)와 판정자(사용자). 골든셋은 행원 질문을 흉내 낸 합성 질의이며 실제 상담 기록이 아니다.
- 데이터 분류: 골든셋은 `SYNTHETIC_WORK`(가상 질문)로 표시하고 정답 ID는 `SYNTHETIC_INTERNAL` 규칙 version을 가리킨다.
- Out of Scope: 검색 구현, 색인, 임베딩 모델 선택, 실제 행원 질문 수집.

| 공문 | 규칙 키 | 규칙 version ID(앞 8자) | 2026-10-06 기준 상태 |
|---|---|---|---|
| 중도상환수수료 v1 (2026-09-15~10-01) | `CHECK_PREPAYMENT_FEE_RATE`(1.2퍼센트) | `82f74fb1…` | 구버전. 테스트용 checklist 근거 → **제외 대상** |
| 중도상환수수료 v1·v2 공통 | `CHECK_NOTICE_SOURCE` | `a72302da…` | v2 승인 항목의 근거 → 사용 가능 |
| 중도상환수수료 v2 (2026-10-01~) | `CHECK_PREPAYMENT_FEE_RATE`(0.8퍼센트) | `0827aed5…` | 승인 항목 근거 → 사용 가능 |
| 중도상환수수료 v2 | `CHECK_CUSTOMER_CONTRACT_DATE` | `6a0041a7…` | 승인 항목 근거 → 사용 가능 |
| 셀러론 v1·v2 | `CHECK_CORPORATE_LIMIT_SOURCE` | `205820d6…` | 다른 공문군. 셀러론 상담에서도 승인 전이면 제외 |
| 셀러론 v2 | `CHECK_SETTLEMENT_EVIDENCE` | `f6f8bc98…` | 미승인 → 제외 |
| 셀러론 v1·v2 | `CHECK_HUMAN_REVIEW` | `daedcfc1…` | 미승인 → 제외 |

"사용 가능"은 골든셋이 정하는 것이 아니라 평가 시점에 Core(Tool 2)가 정한다. 골든셋의 `relevant`는 "그 시점에 Core가 사용 가능하다고 할 때 찾아야 하는 근거"이고, `must_not`은 "어떤 경우에도 나오면 안 되는 근거"다. **다른 공문군 제외**는 "요청 범위(`family_id`) 밖"이라는 뜻이다. 셀러론 규칙이 나쁜 근거라서가 아니라 중도상환수수료 상담 요청 범위에 없기 때문에 제외한다.

## 골든셋 구조

- 파일: `datasets/synthetic/search-goldenset/prepayment-fee-smoke-v1.json`(초기 점검용 10건), `datasets/synthetic/search-goldenset/prepayment-fee-eval-v1.json`(최종 평가용 20~30건). 계약 `contracts/search-goldenset.schema.json`.
- 질의 항목: `query_id`, `query`(행원 질문), `family_id`, `business_date`, `relevant`(규칙 version ID 목록, 순서 무관), `must_not`(규칙 version ID 목록), `expected_hold`(true면 "사용 가능한 근거 없음 → 보류"가 정답), `category`(아래), `rationale`(왜 이 정답인지 한 줄). 파일 머리에 `dataset_class: SYNTHETIC_WORK`, `synthetic: true`, 면책 문구, `goldenset_version`.
- 범주: `direct`(규칙 문구에 가까운 질문), `paraphrase`(다른 말로 묻기), `numeric`(숫자·날짜 질문), `old_value_apply`(구버전 값을 현재 업무에 적용하려는 질문 → 차단·보류), `current_value`(값이 바뀌었는지, 지금 얼마인지 묻는 질문 → 최신 사용 가능 근거 제공), `other_family`(요청 범위 밖 공문군), `unapproved`(미승인 규칙을 묻는 질문), `hold`(관련 근거가 없어 보류), `before_approval`(승인 전 업무일로 묻는 질문 → 보류).
- 구버전 질문의 의도 구분: "1.2퍼센트로 처리해도 되나"처럼 **구버전 값을 현재 업무에 적용**하려는 질문은 구버전 근거를 주지 않고 보류한다. "수수료율이 바뀌었나, 지금 얼마인가"처럼 **현재 값을 묻는** 질문에는 최신 사용 가능 근거(`0827aed5…`)를 준다. "전에는 얼마였고 지금은 얼마인가" 같은 **역사적 비교 조회는 이번 범위 밖**이며 골든셋에 넣지 않는다(과거 기록은 사람용 조회 API의 역할이고 Tool은 현재 시각 기준만 본다).
- 초기 점검용 10건 초안(실행 전에 사용자 확인):

| ID | 질의(행원 말투) | 범주 | 정답 근거(relevant) | 나오면 안 되는 것(must_not) | 보류 | 이유 |
|---|---|---|---|---|---|---|
| S01 | 중도상환수수료율이 바뀌었다는데 지금 얼마예요? | current_value | `0827aed5…` (v2 0.8퍼센트) | `82f74fb1…` (v1 1.2퍼센트) | 아니오 | 현재 값을 묻는 질문. 최신 사용 가능 근거 제공, 구버전은 제외 |
| S02 | 기업여신 중도상환 수수료 0.8퍼센트는 언제부터 적용되나요? | numeric | `0827aed5…` | `82f74fb1…` | 아니오 | 시행일 2026-10-01이 규칙 구조화 값에 있음 |
| S03 | 수수료를 안 받는 예외가 있나요? | paraphrase | `0827aed5…` | — | 아니오 | 예외("별도 약정으로 면제")가 같은 규칙에 있음 |
| S04 | 고객 약정일은 왜 확인해야 하나요? | direct | `6a0041a7…` | — | 아니오 | v2에서 추가된 항목의 근거 |
| S05 | 2026년 10월 1일 이후 중도상환이면 뭘 확인해야 하나요? | numeric | `0827aed5…`, `6a0041a7…` | `82f74fb1…` | 아니오 | 조건("2026-10-01 이후 중도상환")과 약정일 확인 둘 다 해당 |
| S06 | 어느 공문 버전을 보고 안내해야 하나요? | direct | `a72302da…` | — | 아니오 | 공문 버전·원문 위치 확인 규칙(v1·v2 공통이지만 v2 승인 항목의 근거) |
| S07 | 이 고객은 1.2퍼센트로 처리해도 되나요? | old_value_apply | — | `82f74fb1…` | **예** | 구버전 값을 현재 업무에 적용하려는 질문. 구버전 근거를 주지 않고 보류. 현재 기준 안내는 준비안 단계의 몫 |
| S08 | 셀러론 법인 한도 20억 근거 좀 보여 주세요 (중도상환수수료 상담 요청) | other_family | — | `205820d6…` | **예** | 요청 범위(`SIN-PREPAYMENT-FEE`) 밖 공문군. 셀러론 상담으로 요청하면 별도 질의로 평가 |
| S09 | 매출 정산 내역은 어떤 기준으로 확인하나요? | unapproved | — | `f6f8bc98…` | **예** | 셀러론 v2 미승인 규칙. 승인 전 근거는 제공하지 않음 |
| S10 | 이 기업 대출 승인 기준이 뭔가요? | hold | — | 전체 | **예** | 승인·거절 기준은 AI가 다루지 않는다(CLAUDE.md). 관련 근거 없음 → 보류 |

보류(`expected_hold=true`)의 정답은 "재확인 뒤 목록이 비어 있고 보류 사유가 남는 것"이다. S07·S08·S09는 후보 단계에서 metadata 제외 조건에 걸려야 하고(아래 후보 단계 지표), 혹시 후보로 올라와도 Core 재확인이 막아야 한다.

- 최종 평가용 20~30건: 위 범주별 최소 2건(`current_value`와 `old_value_apply`는 각 3건 이상으로 의도 구분을 충분히 시험), `paraphrase`와 `numeric`은 각 5건 이상, 승인 전 업무일(`before_approval`, 2026-09-30 조회 → 보류) 2건 이상, 셀러론을 요청 범위로 한 `other_family` 반대 사례 1건 이상(중도상환수수료 규칙이 제외되어야 함), 오타·띄어쓰기 변형 2건 이상. 초기 점검용 질의는 최종 평가용에 **포함하지 않는다**(점검용으로 맞춘 결과가 평가에 섞이지 않게). 역사적 비교 질의는 넣지 않는다(범위 밖).

## 지표와 계산 방법 (제안, 확인 뒤 확정)

평가는 두 단계로 나눠 측정한다. **최종 사용자 응답 지표**는 "검색 후보 → Core Tool 2 재확인 → 통과한 근거 목록(순위 유지)"으로 계산한다. **후보 단계 지표**는 재확인 전 검색 결과 자체를 본다. 최종 노출이 0건이라도 후보 단계에서 제외 조건을 어겼다면 검색 필터가 틀린 것이므로 둘 다 기록한다.

| 단계 | 지표 | 계산 | 제안 기준(기준선 BM25 / 최종) |
|---|---|---|---|
| 최종 | Recall@5 | 질의별 `relevant` 중 재확인 뒤 상위 5개 안에 든 비율의 평균(`expected_hold=true` 질의 제외) | ≥ 0.8 / ≥ 0.9 |
| 최종 | MRR | 질의별 첫 `relevant`의 순위 역수 평균(없으면 0, hold 질의 제외) | ≥ 0.7 / ≥ 0.8 |
| 최종 | 최종 노출 | 재확인 뒤 목록에 `must_not`이 나온 건수 | **0건(필수)** |
| 최종 | 잘못된 보류(답할 수 있는데 보류) | `expected_hold=false` 질의 중 재확인 뒤 목록이 빈 비율 | ≤ 10% / ≤ 5% |
| 최종 | 놓친 보류(보류해야 하는데 근거 제공) | `expected_hold=true` 질의 중 재확인 뒤 목록이 비어 있지 않은 비율 | **0%(필수)** |
| 후보 | 후보 제외 조건 준수 | 재확인 전 후보 중 metadata 제외 조건(승인 항목 근거만, 요청 `family_id`만, 현재 적용 공문만)을 어긴 건수와 비율 | 0건 목표. 0건이 아니면 검색 필터 결함으로 기록(최종 노출 0건이어도 통과 아님) |
| 후보 | 재확인 제거 수와 이유 | 질의별 Core 재확인이 제거한 후보 수와 사유 코드(`EVIDENCE_NOT_AVAILABLE`의 차단 사유별) | 기록. 제거가 많으면 필터 결함 신호 |
| 후보 | Core 재확인 호출 수 | 질의당 Tool 2 호출 수(후보 수) | 기록 |

- 수치 확정 절차: 골든셋 초안(질문, 정답 근거, 보류 사례)과 위 계산 방법을 사용자가 확인한 뒤 기준값을 확정하고 이 문서의 "판단 기록"에 남긴다. 확정 전에는 제안값이다.
- 재확인이 거부한 후보는 최종 지표에서 "없던 것"으로 보되, 후보 단계 지표에 제거 수와 이유로 남긴다(검색 품질이 좋아도 Core가 막으면 결과가 아니고, Core가 막았다고 필터가 맞는 것도 아니다).

## 평가 스크립트 명세 (구현은 TASK-016)

- 입력: 골든셋 파일 경로, 검색 API 주소, Tool 토큰(환경변수), 평가 고정 조건(`evaluation_context`: 평가 시각, 승인 상태, 자료 해시). 조건이 실제 환경과 다르면 평가를 거부한다.
- 동작: 질의마다 검색 API 호출 → 후보 목록 기록(후보 단계 지표) → 후보별 Tool 2 호출 → 제거된 후보와 사유 기록 → 통과 목록(최종 지표) → 결과 파일 `docs/evidence/SEARCH_EVALUATION_<구성>_<골든셋 버전>.md`(질의별 후보 상위 5개, 제거 사유, 통과 목록, 두 단계 지표 표, 실패 질의 목록).
- 같은 골든셋 버전으로 BM25 기준선과 최종 구성을 각각 실행해 비교표를 만든다. 골든셋을 고치면 버전을 올리고 두 구성을 다시 돌린다.
