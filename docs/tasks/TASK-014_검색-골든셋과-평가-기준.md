# TASK-014 검색 골든셋과 평가 기준 (검색 구현 전)

- 상태: **계획 검토 대기** (상세 계획 작성 승인: 사용자. 제안 3건, 추가 조건 5건, 정답 기준 보완 4건 반영. 골든셋 작성 착수와 검색 구현은 미승인)
- 담당자 / 인간 결정자: AI 조사·초안·골든셋 작성 / 사용자 질문·정답 근거·보류 사례·계산 방법 확인과 수치 확정
- 요구사항 출처: PLAN-002 TASK-014 절과 사용자 판단(초기 점검용 10건과 최종 평가용 20~30건 구분, Recall@5·MRR 수치는 제안값, 확인 뒤 확정), DEVELOPMENT_RULES "검색은 골든셋 버전, Recall@5/MRR 등 지표와 근거성/보류 기준을 구현 전 정의", CLAUDE.md 검색 baseline(BM25 + dense vector k-NN + metadata filter + reranker)
- 관련 Task: TASK-008(완료, Tool 2개), TASK-016(BM25 기준선, 이 Task 뒤), TASK-018(벡터 + reranker, 최종 평가용 골든셋으로 비교)

## Goal / 관련 요구사항

- Goal: 검색을 구현하기 전에 "무엇을 찾아야 정답이고, 무엇이 나오면 안 되며, 언제 보류해야 하는가"를 데이터와 숫자로 고정한다. 이후 TASK-016(BM25)과 TASK-018(벡터 + reranker)은 같은 골든셋으로 비교한다.
- 입력: 합성 공문 4건(중도상환수수료 v1·v2, 셀러론 v1·v2)의 규칙 version ID(아래 표), TASK-007·008로 확정된 "사용 가능" 상태 규칙(승인된 중도상환수수료 v2 항목 3개), 합성 신청 건.
- 출력: 골든셋 파일 2개, 골든셋 계약 schema, 지표 정의와 계산 방법, 평가 스크립트 명세, 통과 기준 확정 기록. **코드 변경 없음**(평가 스크립트 구현은 TASK-016).
- 사용자: 검색 구현자(AI)와 판정자(사용자). 골든셋은 행원 질문을 흉내 낸 합성 질의이며 실제 상담 기록이 아니다.
- 데이터 분류: 골든셋은 `SYNTHETIC_WORK`(가상 질문)로 표시하고 정답 ID는 `SYNTHETIC_INTERNAL` 규칙 version을 가리킨다.
- Out of Scope: 검색 구현, 색인, 임베딩 모델 선택, 실제 행원 질문 수집.

"사용 가능"은 골든셋이 정하는 것이 아니라 평가 시점에 Core(Tool 2)가 정한다. 골든셋의 `relevant`는 "그 시점에 Core가 사용 가능하다고 할 때 찾아야 하는 근거"이고, `must_not`은 "어떤 경우에도 나오면 안 되는 근거"다. **다른 공문군 제외**는 "요청 범위(`family_id`) 밖"이라는 뜻이다. 셀러론 규칙이 나쁜 근거라서가 아니라 중도상환수수료 상담 요청 범위에 없기 때문에 제외한다.

## 두 가지 보류와 "반환할 근거"의 정의

**근거 보류(`expected_evidence_hold`)**: 재확인 뒤 제공할 수 있는 근거가 없어 목록이 비는 것. 검색 필터(승인 항목 근거만, 요청 범위만, 현재 적용 공문만)와 Core 재확인이 만든다. 골든셋 지표(보류 정확도, 잘못된 보류, 놓친 보류)는 **이 보류**를 잰다.

**처리 판단 보류(`requires_human_decision`)**: 근거는 보여 주되 "이 고객을 이렇게 처리해도 되는가"의 판단은 사람에게 남기는 것. 구버전 값을 적용하려는 질문(S07)이나 승인 여부를 묻는 질문(S10)이 여기 해당한다. **이 보류는 질문 의도에 따른 것이라 metadata 필터나 Core의 문서 사용 가능 검사만으로는 만들 수 없다.** 준비안을 만드는 AI 서비스(TASK-015, 규칙 조립)와 후속 LLM 단계(TASK-019), 그리고 사람의 최종 확인(TASK-017)이 담당한다. 골든셋은 이 값을 기록만 하고 검색 지표로 평가하지 않으며, TASK-015 완료 확인 조건에서 따로 검증한다.

**반환할 근거와 DB에만 있는 정보의 구분(사실)**: Tool `rule_evidence`는 규칙 원문 문장(`evidenceText`, 공문 추출 결과의 지시 문장), 원문 위치(`jsonPointer`), 해시만 돌려준다. 시행일, 변경 전후 값, 조건, 예외는 그 문장에 없고 `structured_change`에 있으며, 이 값은 Tool `applicable_checklist`의 항목(`items[].structuredChange`)으로 제공된다. 따라서 검색 결과 하나는 "문장 + 위치"이고, 시행일·예외 같은 값은 같은 항목의 구조화 값을 붙여야 행원이 받는 근거가 된다. 골든셋은 질의마다 `expected_fields`에 어느 값이 최종 근거에 포함돼야 하는지 적고, 평가 스크립트는 (a) 규칙 version이 재확인을 통과했는지, (b) 그 항목의 구조화 값에서 해당 필드를 Tool 1로 실제로 받았는지를 모두 확인한다. DB에만 있고 Tool로 나오지 않는 값(예: 변경안 ID, 검증 issue 세부)은 근거로 치지 않는다.

## 골든셋 구조

- 파일: `datasets/synthetic/search-goldenset/prepayment-fee-smoke-v1.json`(초기 점검용 10건), `datasets/synthetic/search-goldenset/prepayment-fee-eval-v1.json`(최종 평가용 20~30건). 계약 `contracts/search-goldenset.schema.json`.
- 질의 항목: `query_id`, `query`(행원 질문), `family_id`(요청 범위), `business_date`, `relevant`(규칙 version ID 목록, 순서 무관), `must_not`(규칙 version ID 목록), `expected_evidence_hold`(true면 재확인 뒤 목록이 비는 것이 정답), `requires_human_decision`(true면 근거와 별개로 처리 판단을 사람에게 남김, 기록용), `expected_fields`(최종 근거에 포함돼야 하는 구조화 값, 예 `effective_on`, `exceptions`), `category`(아래), `rationale`. 파일 머리에 `dataset_class: SYNTHETIC_WORK`, `synthetic: true`, 면책 문구, `goldenset_version`, `evaluation_context`.
- 범주: `direct`(규칙 문구에 가까운 질문), `paraphrase`(다른 말로 묻기), `numeric`(숫자·날짜 질문), `old_value_apply`(구버전 값을 현재 업무에 적용하려는 질문 → 구버전 근거 제외, 최신 근거 제공, 처리 판단은 사람), `current_value`(값이 바뀌었는지, 지금 얼마인지 묻는 질문 → 최신 사용 가능 근거 제공), `other_family`(요청 범위 밖 공문군), `unapproved`(요청 범위 안이지만 미승인 규칙), `decision_forbidden`(승인 여부를 AI에게 묻는 질문 → 근거 없음, AI는 결정하지 않음), `hold`(관련 근거가 없어 보류), `before_approval`(승인 전 업무일로 묻는 질문 → 보류).
- 구버전 질문의 의도 구분: "1.2퍼센트로 처리해도 되나"처럼 **구버전 값을 현재 업무에 적용**하려는 질문은 구버전 근거(`82f74fb1…`)를 제외하되 **현재 0.8퍼센트 근거(`0827aed5…`)는 제공**하고, 그 고객의 처리 판단은 사람에게 남긴다(`requires_human_decision=true`). "수수료율이 바뀌었나, 지금 얼마인가"처럼 **현재 값을 묻는** 질문에는 최신 근거를 준다. "전에는 얼마였고 지금은 얼마인가" 같은 **역사적 비교 조회는 이번 범위 밖**이며 골든셋에 넣지 않는다(과거 기록은 사람용 조회 API의 역할이고 Tool은 현재 시각 기준만 본다).

| S10 | 이 기업 대출을 승인해도 되나요? | 중도상환수수료 | decision_forbidden | — | 전체 | 예 | **예** | — | AI는 승인·거절을 결정하지 않는다(CLAUDE.md). 답할 근거가 없어 근거 보류이며 결정은 사람. 승인 기준을 설명하는 것 자체를 금지하는 것은 아니다(그런 규칙이 승인되면 근거로 제공할 수 있다) |

근거 보류(`expected_evidence_hold=true`)의 정답은 "재확인 뒤 목록이 비어 있고 보류 사유가 남는 것"이다. S08·S09·S10은 후보 단계 제외 조건에도 걸려야 하고(S10은 관련 문서 자체가 없음), 혹시 후보로 올라와도 Core 재확인이 막아야 한다. S07은 근거 보류가 아니다. 근거는 나오되 처리 판단이 사람에게 남는 사례이며 검색 지표에서는 `relevant`·`must_not`으로만 평가한다.

- 최종 평가용 20~30건: 위 범주별 최소 2건(`current_value`와 `old_value_apply`는 각 3건 이상으로 의도 구분을 충분히 시험, `decision_forbidden` 2건 이상), `paraphrase`와 `numeric`은 각 5건 이상, 승인 전 업무일(`before_approval`, 2026-09-30 조회 → 근거 보류) 2건 이상, 셀러론을 요청 범위로 한 `other_family` 반대 사례 1건 이상(중도상환수수료 규칙이 제외되어야 함), 오타·띄어쓰기 변형 2건 이상. 초기 점검용 질의는 최종 평가용에 **포함하지 않는다**. 역사적 비교 질의는 넣지 않는다(범위 밖).

## 지표와 계산 방법 (제안, 확인 뒤 확정)

평가는 두 단계로 나눠 측정한다. **최종 사용자 응답 지표**는 "검색 후보 → Core Tool 2 재확인 → 통과한 근거 목록(순위 유지)"으로 계산한다. **후보 단계 지표**는 재확인 전 검색 결과 자체를 본다. 최종 노출이 0건이라도 후보 단계에서 제외 조건을 어겼다면 검색 필터가 틀린 것이므로 둘 다 기록한다.

| 단계 | 지표 | 계산 | 제안 기준(기준선 BM25 / 최종) |
|---|---|---|---|
| 최종 | Recall@5 | 질의별 `relevant` 중 재확인 뒤 상위 5개 안에 든 비율의 평균(`expected_evidence_hold=true` 질의 제외) | ≥ 0.8 / ≥ 0.9 |
| 최종 | MRR | 질의별 첫 `relevant`의 순위 역수 평균(없으면 0, hold 질의 제외) | ≥ 0.7 / ≥ 0.8 |
| 최종 | 최종 노출 | 재확인 뒤 목록에 `must_not`이 나온 건수 | **0건(필수)** |
| 최종 | 잘못된 보류(답할 수 있는데 보류) | `expected_evidence_hold=false` 질의 중 재확인 뒤 목록이 빈 비율 | ≤ 10% / ≤ 5% |
| 최종 | 놓친 보류(보류해야 하는데 근거 제공) | `expected_evidence_hold=true` 질의 중 재확인 뒤 목록이 비어 있지 않은 비율 | **0%(필수)** |
| 최종 | 필드 제공 | `expected_fields`가 있는 질의 중 해당 값을 Tool 1 항목의 구조화 값으로 실제로 받은 비율 | 100% |
| 후보 | 후보 제외 조건 준수 | 재확인 전 후보 중 metadata 제외 조건(승인 항목 근거만, 요청 `family_id`만, 현재 적용 공문만)을 어긴 건수와 비율 | 0건 목표. 0건이 아니면 검색 필터 결함으로 기록(최종 노출 0건이어도 통과 아님) |
| 후보 | 재확인 제거 수와 이유 | 질의별 Core 재확인이 제거한 후보 수와 사유 코드(`EVIDENCE_NOT_AVAILABLE`의 차단 사유별) | 기록. 제거가 많으면 필터 결함 신호 |
| 후보 | Core 재확인 호출 수 | 질의당 Tool 2 호출 수(후보 수) | 기록 |

- 수치 확정 절차: 골든셋 초안(질문, 정답 근거, 보류 사례)과 위 계산 방법을 사용자가 확인한 뒤 기준값을 확정하고 이 문서의 "판단 기록"에 남긴다. 확정 전에는 제안값이다.
- 재확인이 거부한 후보는 최종 지표에서 "없던 것"으로 보되, 후보 단계 지표에 제거 수와 이유로 남긴다(검색 품질이 좋아도 Core가 막으면 결과가 아니고, Core가 막았다고 필터가 맞는 것도 아니다).

## 평가 스크립트 명세 (구현은 TASK-016)

- 입력: 골든셋 파일 경로, 검색 API 주소, Tool 토큰(환경변수), 평가 고정 조건(`evaluation_context`: 평가 시각, 승인 상태, 자료 해시). 조건이 실제 환경과 다르면 평가를 거부한다.
- 동작: 질의마다 검색 API 호출 → 후보 목록 기록(후보 단계 지표) → 후보별 Tool 2 호출 → 제거된 후보와 사유 기록 → 통과 목록(최종 지표) → 결과 파일 `docs/evidence/SEARCH_EVALUATION_<구성>_<골든셋 버전>.md`(질의별 후보 상위 5개, 제거 사유, 통과 목록, 두 단계 지표 표, 실패 질의 목록).
- 같은 골든셋 버전으로 BM25 기준선과 최종 구성을 각각 실행해 비교표를 만든다. 골든셋을 고치면 버전을 올리고 두 구성을 다시 돌린다.

### 정답 기준 보완 (사용자 지시, 반영)
- S07: 구버전 근거는 제외하되 현재 0.8퍼센트 근거 제공은 막지 않는다. 최신 근거 제공과 그 고객의 처리 판단 보류를 구분한다(`expected_evidence_hold`와 `requires_human_decision`). 의도에 따른 보류는 metadata 필터나 Core의 문서 사용 가능 검사만으로 만들 수 없다고 명시.
- S09: 요청 범위를 셀러론으로 지정해 "범위는 맞지만 미승인이라 차단"되는 사례로 변경.
