## Goal / 관련 요구사항

- Goal: 행원이 담당 상담 건을 열면 질문하지 않아도 적용 공문, 승인 Checklist, 규칙 원문 근거가 먼저 보이고, AI 준비안(READY/PARTIAL/HOLD)을 만들어 보류 사유를 확인하며, 항목별 근거를 확인했다는 기록을 남긴다.
- 사용자: 합성 직원 `SYN-STAFF-01`(STAFF), `SYN-REVIEWER-01`(REVIEWER), `SYN-STAFF-REVIEWER-01`(둘 다, 역할 전환).
- 업무규칙: (1) 화면은 Core만 부른다. AI 서비스는 Core를 통해서만 호출된다. (2) 화면에 보이는 규정·항목·근거 문장은 Core 응답에서만 온다. (3) 임시 데이터·가짜 AI 응답으로 화면을 채우지 않는다. 미연결 기능은 미연결로 표시한다. (4) 직원 확인은 "근거를 확인했다"는 기록이며 대출 승인·거절, 금리·한도 확정, 신용등급 결정이 아니다. 화면과 기록에 그런 값이 없다. (5) 보류(HOLD) 섹션은 확인 기록 대상이 아니다. (6) 합성 자료임을 화면에 표시한다.
- Out of Scope: 근거 검색·질문 응답·RAG(TASK-016·017c), 검수자 승인 쓰기 화면(TASK-027, 이번에는 읽기 전용 목록만), 체험 코드(TASK-026), 배포 패키징(TASK-023), 상담 메모·고객 정보 입력, 재배정, 모바일 레이아웃(태블릿·데스크톱 폭 우선).

## 기존 API 재사용과 필요한 추가

| 화면 기능 | 사용하는 API | 상태 |
|---|---|---|
| 로그인·로그아웃·세션·역할 전환 | `POST /login`, `POST /logout`, `GET /api/v1/session`, `POST /api/v1/session/active-role` | 기존 |
| 상담 건 생성·목록·상세 | `POST/GET /api/v1/consultations`, `GET /api/v1/consultations/{id}` | 기존, **응답 확장**(아래 1) |
| 적용 공문·Checklist·규칙 원문 근거·보류 사유 | `GET /api/v1/internal-policy/checklists/{familyId}/applicable?businessDate=` | 기존 그대로(규칙 `evidenceText`·`jsonPointer`·`evidenceHash`, 승인 항목, `blockingReasons` 포함) |
| 공개 상품 관측 상태 | `GET /api/v1/public-products/{productKey}/observed-state` | 기존 그대로 |
| AI 준비안 생성 | `POST /api/v1/consultations/{id}/preparation` | 기존 그대로 |
| 검수자 화면(읽기 전용) | `GET /api/v1/reviews/proposals` | 기존 그대로 |
| 상담 건 생성용 신청 선택 | 없음 | **신규 2** |
| 저장된 준비안 다시 보기 | 없음(생성 응답만 있음, 새로고침하면 사라짐) | **신규 3** |
| 직원 확인 기록·조회 | 없음 | **신규 4** |
| 화면 정적 자원 | 없음 | **신규 5** |

1. **상담 건 응답 확장**(새 경로 아님): 상세·목록 응답에 신청 요약(합성 기업명, 신청 금액, 목적, 신청 시각, 상태)과 상품의 공문군 목록(`familyId`, `required`, 매핑 순서)을 더한다. 화면이 공문군별 적용 checklist를 부를 근거다.
2. `GET /api/v1/applications`(STAFF): 업무 DB에 등록된 합성 신청 목록(신청 ID, 기업명, 상품, 금액, 목적). 상담 건 생성 대화상자에서 고른다.
3. `GET /api/v1/consultations/{id}/preparation`(STAFF, 담당자만): 그 상담 건에 기록된 최신 준비안(준비안 ID, 상태, 업무일, 섹션별 상태·보류 사유 코드·승인 checklist version·결정 ID·항목 규칙 version·근거 해시, 기록 시각). 없으면 404 `PREPARATION_NOT_FOUND`.
4. 직원 확인: 업무 DB `V12 consultation_confirmation`(append-only, 보호 목록 등록). 같은 V12에 상담 건-준비안 연결 `consultation_preparation_link`(아래 AC-15), `POST /api/v1/consultations/{id}/confirmations` `{preparationId, familyId, ruleVersionIds[]}`, `GET`으로 목록. 기록 조건: 담당자(아니면 404), STAFF 활성, 준비안이 이 상담 건의 것, 섹션이 READY(HOLD면 409 `SECTION_ON_HOLD`), `ruleVersionIds`가 그 섹션 항목 전체와 같음(일부면 422 `CONFIRMATION_INCOMPLETE`), 기록 시점에 Core가 같은 업무일로 다시 조회해 사용 가능하고 승인 checklist version·결정 ID가 준비안과 같음(다르면 409 `PREPARATION_STALE`), 같은 준비안·공문군 재확인은 409 `ALREADY_CONFIRMED`. 행에는 principal, 실제 활성 역할, 준비안 ID, 공문군, 승인 checklist version, 결정 ID, 확인한 규칙 version과 근거 해시, 시각을 남긴다. 승인·거절·금리·한도 열은 없다.
5. Core 보안 체인: 정적 자원(`/`, `/index.html`, `/assets/**`)을 permitAll로 열고, `/api/**`·`/login`·`/logout`·`/actuator/**`가 아닌 GET은 `index.html`로 넘긴다(SPA 경로). API 경로의 인증·권한 규칙은 바꾸지 않는다.

## 화면 구성

기술: React + TypeScript + Vite, shadcn/ui(Radix + Tailwind, 컴포넌트 소스 포함), React Router, TanStack Query, lucide 아이콘. 의존성은 정확한 버전과 `package-lock.json`으로 고정한다. 빌드 결과는 Core가 정적 자원으로 제공한다(같은 출처 세션 쿠키, `XSRF-TOKEN` 쿠키 → `X-XSRF-TOKEN` 헤더).

디자인 기준: KB국민은행 태블릿 브랜치 리뉴얼의 색상·여백·큰 터치 영역(노랑 계열 강조색, 짙은 회갈색 본문, 따뜻한 회색 배경)을 참고하되 **KB 로고·워드마크·서비스명은 쓰지 않는다.** MyStar처럼 고객(기업) → 신청 → 상담 건 순서로 정보를 묶고, Service Console처럼 좌측 목록 · 중앙 업무 · 우측 보조 패널의 3단 구성을 쓴다. 태블릿 가로(1024px)와 데스크톱(1280px 이상)을 기준으로 한다.

```text
┌ 상단: TrustAgent · 합성 자료 표시 · 사용자 · 활성 역할 전환 · 로그아웃 ─────────────────────┐
│ 좌측(접힘 가능)        │ 중앙: 상담 상세                                 │ 우측(접이식) AI 업무지원 │
│ 담당 상담 건 목록       │ ┌ 기업·신청 요약(기업명, 상품, 금액, 목적, 업무일) ┐ │ 준비안 상태 READY/       │
│ - 검색어 필터(목록 안)  │ ├ 공문군별 카드                                  ┤ │   PARTIAL/HOLD           │
│ - 새 상담 건           │ │  적용 공문(제목·버전·시행일) · 사용 가능/보류  │ │ 섹션별 상태·보류 사유    │
│                        │ │  Checklist 항목(지시 문장, 변경 값, 근거 필수) │ │ [준비안 만들기]          │
│                        │ │   └ 규칙 원문 근거(문장·위치·해시) 펼치기       │ │ 직원 확인 기록 상태      │
│                        │ │  항목별 "근거 확인" 체크 → [확인 기록]         │ │ 질문 응답: 검색 연결 전  │
│                        │ └ 보류 공문군: 사유와 "수기 확인" 안내           ┘ │  (미연결 표시)           │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

화면 목록: 로그인, 상담 건 목록(STAFF 첫 화면), 상담 상세(위 구성), 검수 대기 목록(REVIEWER 첫 화면, 읽기 전용, 결정은 TASK-027 안내), 오류(401은 로그인으로, 403은 역할 안내, 404는 "상담 건을 찾을 수 없음").

화면 동작: 상세 진입 시 공문군별 적용 checklist와 저장된 최신 준비안을 함께 읽는다(질문 없이 먼저 보임). 준비안 만들기는 Core를 거쳐 AI 서비스를 부르고, 502·504면 "AI 준비안 없음"과 함께 Core의 적용 checklist를 그대로 수기 확인용으로 보인다. 보류 사유는 코드와 한국어 설명을 함께 보이며 모르는 코드는 코드 그대로 보인다. 직원 확인 버튼은 READY 섹션에서 모든 항목을 체크했을 때만 켜지고, 서버 거부는 사유를 그대로 보인다. 직원 확인 영역에 "대출 승인·거절이 아닌 근거 확인 기록"임을 적는다. 역할 겸임 사용자에게는 직무 분리와 다르다는 안내를 보인다(ADR-014 6항).

- 같은 신청의 여러 상담 건: 준비안 ID가 상담 ID를 빼고 계산돼 `consultation_preparation.consultation_id`는 처음 기록한 상담 건만 가리킨다. 이를 그대로 쓰면 두 번째 상담 건의 준비안이 사라지거나 다른 상담 건에 붙는다. 연결 표로 해결했으며 V12 이전에 기록된 준비안에는 연결이 없어 조회되지 않는다(합성 환경이라 재생성으로 해결).
- 화면 업무일 기본값은 브라우저의 서울 기준 오늘이다. E2E는 고정 시계(2026-10-06)에 맞춰 URL로 업무일을 지정한다.
- 접근성 검사가 보류 색 대비 미달(4.46)을 찾아 고쳤다. axe는 자동 검사 범위만 보장한다.
- jsdom 30이 Node 24.15 이상을 요구해 로컬(24.14)에서 경고가 난다. 테스트는 통과했고 CI는 Node 24 최신을 쓴다.
