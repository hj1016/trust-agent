# ADR 012 AI 서비스 산출물 기록 경로와 기록 권한

## 상태

**초안.** ADR 자체는 미승인이며 TASK-015 계획 PR에서 검토한다. 다만 아래 "사용자 판단"에 적은 **방향**(기록 경로는 Tool 밖, 읽기·기록 토큰 분리, ID·해시·버전 중심 기록, 준비안 ID와 실행 ID 분리, 필수 공문군 기준 상태, 메모 입력 제외)은 사용자가 TASK-015 제안 6건으로 채택했다. 세부 설계(표 구조, 오류 코드, 검사 순서)는 계획 PR 검토 사항이며 이 문서의 "결정"은 그 검토 전까지 초안이다.

## 배경

ADR-011은 AI 서비스가 Core에서 읽을 수 있는 경계를 정했다. 읽기 전용 Tool 2개, 서비스 토큰 1개, 감사 기록, **쓰기 Tool 없음**이다. TASK-015는 AI 서비스가 Tool로 읽은 승인 checklist로 상담 준비안을 규칙으로 조립하거나 보류하고, 그 결과를 Core에 남기려 한다(PLAN-002 제안 2 채택: Tool이 아닌 별도 쓰기 경로, 저장 전 Core 재확인). 기록이 없으면 "무엇을 보여 줬는지"를 나중에 확인할 수 없고, 기록이 느슨하면 AI가 보낸 "사용 가능하다"는 주장이 그대로 저장돼 사람 승인 전 기준이 업무에 쓰일 수 있다. 또 읽기용 토큰으로 기록까지 허용하면 권한이 늘어난다.

## 결정 (초안)

### 기록 경로

1. **Tool이 아니다.** 기록 경로는 `POST /api/v1/consultation-preparations`이며 `/api/v1/tools/` 밖에 있고 Tool allowlist에 넣지 않는다. ADR-011의 "쓰기 Tool 없음"은 그대로다.
2. **산출물만 기록한다.** 이 경로는 AI 서비스가 만든 상담 준비안과 보류 결과, 그리고 실행 기록을 새 표 세 개(`consultation_preparation`, `consultation_preparation_section`, `consultation_preparation_run`, 전부 append-only·보호 목록)에 INSERT만 한다. 공문 승인 상태, 적용 일정, 변경안, 검증 결과, 공문 사건, 감사 표는 읽기만 하고 바꾸지 않는다. 통합 테스트가 기록 호출 전후로 이 표들의 행 수가 같음을 확인한다.
3. **저장 전 Core가 다시 확인한다.** 준비된(READY) 섹션마다 같은 공문군·업무일로 적용 공문 조회를 다시 실행해 사용 가능 여부, 승인 checklist version ID·결정 ID, 항목 규칙 version ID 목록(순서 포함), 항목 근거 해시, 선택 공문 ID가 보낸 값과 같은지 확인한다. 하나라도 다르면 준비안 전체를 거부하고 실행 기록에 REJECTED로 남긴다. 부분 저장은 없다.
4. **보류 결과도 기록하되 검사 없이 받지는 않는다.** 모든 요청은 인증, 기록 schema와 결정 필드 없음, 준비안 ID 해시 일치, 승인된 공문군 매핑과 필수 여부·상태 일치, 보류 섹션의 항목·근거·version·결정 ID 공란을 검사한다. 통과한 보류(HOLD) 섹션은 Core가 직접 판정한 보류(`CORE_DECISION`, 근거 `CORE_REPORTED`)와 서비스가 보고한 통신·인증·응답 오류 보류(`UNVERIFIED`, 근거 `SERVICE_REPORTED`)를 구분해 저장하고, 저장 시 Core가 다시 조회한 현재 상태를 함께 적는다. **기록은 보류 사유의 진실성을 보증하지 않는다.** Core가 보증하는 것은 저장 시점에 Core가 직접 본 상태뿐이고, AI가 보낸 사유 코드와 통신 오류는 "서비스가 그렇게 보고했다"는 사실로만 남는다. 재조회 결과가 달라도 섹션 상태를 고치지 않고 둘 다 저장한다.
5. **승인된 매핑을 Core도 확인한다.** 상품별 공문군과 필수 여부는 하나의 설정 파일(현재는 **합성 시나리오의 사용자 승인 설정**이며 실제 승인 부서가 있는 것이 아니다)을 Core와 AI 서비스가 함께 쓴다. Core는 요청의 매핑 해시, 필수 섹션 누락, 필수 여부 변경, 섹션 상태와 다른 전체 READY 주장을 거부한다. 필수 공문군이 하나도 없는 설정에서는 READY를 허용하지 않는다. READY는 "승인된 매핑에 따른 필수 준비 자료를 갖췄다"는 뜻이며 상담이나 대출 결정의 완료가 아니다.
6. **기록은 사용 허가가 아니다. 격리의 보장 범위.** 재확인과 저장은 하나의 DB 트랜잭션에서 SERIALIZABLE 격리로 실행한다. 이는 "재확인이 읽은 승인·일정·공문 사건 행과, 같은 시간에 그 행을 바꾸는 다른 트랜잭션이 직렬로 실행된 것과 같은 결과"를 보장해, 재확인이 본 상태와 저장된 기록이 어긋나는 일을 막는다. **기록 트랜잭션이 커밋된 뒤에 일어나는 철회·반려는 막지 못하며 막는다고 표현하지 않는다.** 그래서 기록 행은 "그 시점에 Core가 사용 가능하다고 확인했다"는 증거이고, 준비안을 보여 주거나 쓰는 쪽(TASK-017)은 그때 Tool 1로 사용 가능 여부를 다시 확인한다. 재시도는 직렬화 실패(SQLSTATE 40001)가 난 그 DB 트랜잭션에 한정해 1회, 재확인부터 다시 한다. Tool 호출과 HTTP 요청은 재시도하지 않는다. 실행 기록은 요청당 1건이며 재시도 횟수만큼 늘지 않고, 재시도 실패는 FAILED(`SERIALIZATION_FAILED`) 1건, 같은 실행 ID 재전송은 409로 거부한다.
7. **멱등과 재실행.** 준비안 ID는 업무 내용의 canonical sha256이고 실행 ID는 요청마다 새 값이다. 재실행은 기존 기록이 있어도 현재 상태를 Tool로 다시 확인한다. Core는 본문으로 해시를 다시 계산해 ID와 비교하고(다르면 400), 같은 ID·같은 내용의 재기록은 새 행 없이 ALREADY_RECORDED로 답하며 실행 기록만 새로 남긴다. 같은 ID·다른 내용은 409로 거부한다.
8. **근거 원문·메모·토큰은 저장하지 않는다.** 규칙 version ID와 근거 해시, checklist version·결정 ID, 신청 자료 해시, 조립 규칙 버전, 문구 표 해시, Tool 응답 해시로 재구성과 대조를 가능하게 한다.

### 기록 권한

9. **누가:** 기록 토큰 `TRUST_AGENT_PREPARATION_RECORD_TOKEN`을 가진 호출자. 토큰에 묶인 서비스 ID(`ai-service`)와 토큰 종류(`record`)만 기록하고 본문의 actor·service 문자열은 쓰지 않는다. 읽기 토큰(`TRUST_AGENT_TOOL_SERVICE_TOKEN`)으로는 기록할 수 없고(401), 기록 토큰으로는 Tool을 읽을 수 없다(401).
10. **무엇을:** 위 세 표에 INSERT. 그 밖의 어떤 표에도 쓰지 못한다.
11. **무엇을 못 하는지:** 기록의 수정·삭제(append-only), 승인·반려·수정 결정, 일정 변경, 변경안 생성·검증 실행, 공문 상태 변경, 감사 표 변경, 사용 허가 부여, 다른 서비스 ID로의 기록.
12. **제공 방식:** 두 토큰 모두 환경변수로만 제공한다. 저장소 파일, 예시 설정, 테스트 코드, 로그, 출력에 실제 값을 남기지 않는다. 테스트는 실행 중 생성한 임시 값을 쓴다. production profile은 둘 중 하나라도 없으면 기동을 거부한다. 선택지: 기록 표에만 INSERT 권한을 가진 별도 DB 역할을 두어 권한을 DB에서도 막는다(이번 단계 기본안은 코드 범위 + 통합 테스트이며, 별도 역할은 운영 전환 시 검토).

### 실패 처리

13. **인증 실패:** 401. 아무것도 저장하지 않고 실행 기록도 남기지 않는다(인증 전이라 서비스 ID를 신뢰할 수 없다). AI 서비스 출력은 `recorded=false`와 사용 금지 안내, 종료 코드 3.
14. **재확인 거부(422 사용 불가, 409 불일치·충돌, 400 schema·ID 불일치):** 준비안 행 없음. 실행 기록 REJECTED(코드 포함)를 REQUIRES_NEW로 남긴다. AI 서비스 출력은 `record.status=REJECTED`, 사용 금지와 재실행 안내, 종료 코드 3.
15. **저장 실패(DB 오류, 제약 위반, 직렬화 재시도 소진):** 500. 롤백 뒤 실행 기록 FAILED를 REQUIRES_NEW로 남긴다. 실행 기록 저장마저 실패하면 `FAILURE_AUDIT_WRITE_FAILED`로 응답한다(TASK-007·008과 같은 방식). AI 서비스는 `recorded=false`.
16. **AI 서비스의 Tool 호출 실패:** 기록 경로와 무관하게 해당 섹션은 `UNVERIFIED` 보류이며 추측 준비안을 만들지 않는다. 기록 토큰이 유효하면 보류 결과는 기록된다.
17. **자동 재시도 없음.** 직렬화 실패가 난 DB 트랜잭션의 1회 재시도 외에는 재시도하지 않는다. 사람이 다시 실행하며 멱등으로 안전하다.

## 근거

- CLAUDE.md: AI 서비스는 업무 DB 직접 접근과 자격증명 보유 금지, Core가 업무 규칙·권한·상태·트랜잭션·감사를 소유.
- DEVELOPMENT_RULES: 최소 권한, 감사 추적, fail-closed, "기록 없는 제공 없음", 미승인·철회·구버전 근거 제외, Core 재확인.
- ADR-011: 읽기 Tool 경계와 서비스 토큰 방식. 이 ADR은 그것을 바꾸지 않고 기록 경로를 추가한다.
- 대안 검토: (a) 쓰기 Tool 추가 → ADR-011 위반. (b) 같은 토큰으로 기록 → 권한 확대, 유출 시 범위 확대. 비용 차이가 작아 분리를 택한다. (c) AI 서비스 로컬 파일 기록 → Core 재확인과 감사 상실. (d) 기록 없이 출력만 → 나중에 확인 불가, MVP 7단계 요구와 어긋남.

## 결과 (승인되면)

- AI 서비스는 읽기 토큰으로 승인되고 사용 가능한 기준만 읽고, 기록 토큰으로 자기 산출물만 남긴다. 업무 상태를 바꾸는 경로는 없다.
- 기록은 재구성과 대조의 근거이지 사용 허가가 아니며, 사용 허가는 매번 Core 재확인으로 얻는다.
- 운영 전환 시 두 토큰을 조직 인증 체계로 바꾸고, 별도 DB 역할과 사용자별 권한을 검토한다(후속 ADR).

## 사용자 판단 (방향, TASK-015 제안 6건 채택)

- 결정자 / 검토 대상: 사용자 / TASK-015 계획 PR
- 채택한 방향: (1) 필수 공문군 기준 READY/PARTIAL/HOLD와 미완료 안내. (2) 준비안 ID와 실행 ID 분리, 재실행 시 현재 상태 재확인. (3) 원문 중복 저장 대신 ID·해시·버전 중심 기록. (4) 이번 단계에서 행원 메모 입력 제외(안전성 책임은 TASK-015 구조 검증, TASK-019 질문 기반·LLM 출력 검증). (5) 읽기·기록 토큰 분리. (6) Java와 Python을 연결하는 자동 검증을 필수 CI에서 실제 실행.
- 함께 지시한 조건: 보류 섹션도 공통 검사를 거치고 기록이 보류 사유의 진실성을 보증하지 않음을 명시. Core가 승인된 매핑과 필수 여부를 확인하고 필수 섹션 누락·필수 여부 변경·거짓 READY를 거부. 필수 공문군 없는 설정은 준비 완료가 아님. READY는 상담·대출 결정의 완료가 아님. SERIALIZABLE의 보장 범위와 1회 재시도 대상을 정확히 적고 저장 뒤 철회까지 막는다고 쓰지 않음.

## 세부 설계 (계획 PR 검토 사항, 이 ADR이 확정하지 않음)

- 표 구조와 열 이름, CHECK 제약, 보호 목록 등록 방식.
- 오류 코드 이름과 HTTP 상태의 대응, 검사 순서(인증 → schema → ID 해시 → 매핑 → 보류 공란 → 재확인).
- 기록 토큰의 설정 이름, 필터 구현, production 기동 거부 조건.
- 별도 DB 역할 도입 시점.
- 안전성 참조 자료의 책임 표시 변경 방식(TASK-015 제안 7).
