# ADR 014 사용자 인증, 객체 권한, AI 요청 승인(grant), 체험 세션의 보안 경계

## 상태

초안 (승인 대기. 결정자 사용자. 방향은 사용자 확인: 브라우저 → Core → AI 서비스 단일 진입, Spring Security 세션, 상담 건별 객체 권한, grant, 체험 코드 세션, 체험 공간 DB 격리)

이 프로젝트는 공개 정보와 합성 자료로 만드는 개발 프로젝트다. 여기서 정하는 인증·권한·체험 통제는 실제 금융기관의 보안 체계나 직무 분리를 완전히 구현한 것이 아니며 그렇게 표현하지 않는다.

## 배경

ADR-011과 012는 AI 서비스가 Core를 읽고 기록하는 경계를 서비스 토큰 두 개로 정했고 사용자별 인증·권한은 후속 ADR로 미뤘다. 클라우드 배포(접근 제한형 AWS)와 외부 평가자의 체험(HTTPS URL + 기간 제한 체험 코드)을 하려면 다음이 필요하다. (1) 비인증 업무 API 접근 차단. (2) 상담 ID 변경 조회 같은 객체 단위 권한 우회 차단. (3) 서비스 토큰이 새도 사용자 권한을 넘어 조회·기록하지 못하게 하는 장치. (4) 체험자마다 변경 상태와 실행 기록을 격리하되 변경안 생성·검증·승인, 상담 준비안, 근거 검색, 최종 확인 기록을 기능 제한 없이 수행하게 하는 구조. (5) 체험 과정에서 반복 인증이나 짧은 만료가 기능 사용을 방해하지 않는 것.

코드 확인 결과 공문 버전·승인 일정·변경안 사슬의 유일 제약은 공문군을 전역 키로 쓰고 보호 함수는 public 스키마를 하드코딩한다. 따라서 workspace 열을 더하는 논리적 격리로는 "체험자 A의 승인이 B의 적용 규정을 바꾸지 않는다"를 보장할 수 없다.

## 결정

### 진입 구조와 서비스 인증

1. **브라우저는 Core만 부른다.** 화면은 Core가 정적 자원으로 제공하고 같은 출처의 세션 쿠키(HttpOnly, Secure, SameSite=Lax)로 호출한다. 브라우저 JavaScript에는 어떤 서비스 토큰도 없다. CSRF는 Spring Security의 쿠키 토큰 방식으로 사용자에게 보이지 않게 처리한다.
2. **Core가 AI 서비스를 내부망에서 부른다.** 준비안·검색 요청은 Core 경로가 세션과 객체 권한을 검사한 뒤 AI 서비스 수신 토큰(`TRUST_AGENT_AI_INBOUND_TOKEN`)으로 호출한다. AI 서비스는 Docker 내부 네트워크에만 있고 사용자 신원을 받지 않는다. AI 서비스 → Core Tool·기록 경로의 기존 방향과 토큰(ADR-011·012)은 그대로다.
3. **FastAPI, Elasticsearch, PostgreSQL은 외부에 노출하지 않는다.** 외부에 여는 것은 HTTPS 종단 프록시 하나다.

### 사용자 인증, 역할, 객체 권한

4. **Core가 사용자 인증과 객체 권한을 소유한다.** Spring Security 세션 인증. 역할은 STAFF와 REVIEWER 두 개이며 ADMIN 역할과 가입·비밀번호 재설정·관리 화면은 만들지 않는다. 운영 workspace의 합성 사용자는 bootstrap runner가 환경변수의 비밀번호로 적재한다.
5. **상담 건은 Core의 객체다.** `consultation` 표(상담 ID, 신청 ID, 담당 사용자, 상태, append-only)를 두고, 상담 건을 다루는 모든 경로는 "현재 principal이 담당자인가"를 검사한다. 클라이언트가 보낸 사용자 ID나 역할 문자열은 쓰지 않는다. 재배정은 범위 밖이다.
6. **활성 역할은 서버가 관리한다.** principal이 STAFF와 REVIEWER를 모두 가질 수 있다(체험자). 역할 전환은 `POST /api/v1/session/active-role`로 세션 속성을 바꾸는 서버 호출이며 재로그인이 없다. 각 경로는 "principal이 그 역할을 가진다"와 "현재 활성 역할이 그 역할이다"를 둘 다 검사한다. 화면 표시만 바꾸는 전환은 허용하지 않는다. 사람 결정, 확인 기록, 감사 행에는 principal과 **실제 수행 역할**을 함께 남긴다. 이 역할 겸임은 체험을 위한 단순화이며 실제 금융기관의 직무 분리(작성자와 승인자 분리)와 다르다는 점을 화면과 문서에 적는다.

### AI 요청 승인(grant)

7. **서비스 토큰만으로는 Tool과 기록 경로를 쓸 수 없다(require-grant 모드).** Core는 사용자와 상담 건 검사를 통과한 요청마다 `ai_request_grant` 행(승인 ID 32 hex, workspace, 상담 ID, 신청 ID, 허용 공문군 목록(승인된 매핑), 업무일, 사용자 ID, 활성 역할, 만료 60초, 읽기 호출 수, 기록 사용 여부)을 만들어 AI 서비스에 넘기고, AI 서비스는 Tool 1·2와 기록 경로 호출마다 `X-TrustAgent-Grant` 헤더로 보낸다. Core의 Tool·기록 필터는 서비스 토큰 **그리고** 승인 ID를 요구한다.
8. **Core는 grant에서 workspace를 읽어 라우팅을 정한다.** AI 서비스가 보내는 어떤 값도 workspace 선택에 쓰지 않는다. 검사 순서는 토큰 → grant 존재·만료 → workspace 유효 → 상담 ID 일치 → `familyId` ∈ 허용 공문군 → (기록) 신청 ID 일치와 원자적 사용 처리(`UPDATE ... WHERE consumed = false`).
9. **수용 기준.** 만료 뒤 403 `GRANT_EXPIRED`. 읽기 호출 50회 초과 403 `GRANT_EXHAUSTED`. 기록은 1회이며 재시도 409 `GRANT_CONSUMED`, 동시 두 기록은 하나만 201. 정리·만료된 workspace의 grant 403 `WORKSPACE_UNAVAILABLE`. 범위 밖 공문군·상담 ID·신청 ID 403. grant 저장 실패면 AI 서비스를 부르지 않고 500(내부 정보 비노출). AI 호출 실패면 grant는 사용되지 않은 채 만료. grant 발급과 사용은 제어 DB의 append-only 표에 남긴다.
10. **모드 구분.** `trust-agent.tool-api.require-grant=false`는 로컬 CLI·하네스(TASK-015·021) 전용이며 cloud·prod profile은 true가 아니면 기동을 거부한다. demo 설정은 운영 통제가 아니다.

### 체험 세션과 체험 공간

11. **체험 코드 입력이 곧 로그인이다.** `POST /api/v1/trial/sessions`는 한 요청 안에서 코드 검증(SHA-256 해시 저장, 상수 시간 비교, 유효 기간·폐기·코드당 생성 상한·IP와 코드별 시도 제한), 용량 확인, 체험 공간 생성, 합성 principal `TRIAL-<workspace>`(STAFF·REVIEWER)의 Spring Security 세션 발급을 끝낸다. 비밀번호, 가입, 이메일 등록, VPN, 추가 로그인은 없다. 유효한 세션에서는 반복 인증 없이 업무 기능을 쓴다.
12. **체험 공간은 DB 단위로 격리한다.** 체험 공간마다 업무 템플릿 DB에서 복제한 PostgreSQL 데이터베이스와 ES 색인을 가진다. 템플릿은 Flyway 전체와 기존 runner(공개 상품 baseline, 합성 공문, 예시 checklist, 매핑, 변경안 생성·자동 검증)를 적용한 "검토 대기" 상태다. 제어 DB(`trust_agent_control`)는 체험 코드·시도·공간·사건·사용자·grant를 갖고 업무 표와 분리한다. 운영 workspace `main`도 같은 구조의 업무 DB다. 체험 경로에서 `main`과 템플릿에 쓰는 경로는 없다. 복제는 CREATEDB만 가진 provisioner 계정이 하며 업무 표 권한이 없다.
13. **세 수명을 분리한다(설정값, 초기 제안).** 체험 코드 유효 기간(새 공간 생성 가능 기간: 공용 60일, 개별 14일), 세션 만료(유휴 8시간, 절대 24시간), 체험 공간 수명(생성 뒤 7일, 유휴 3일). 코드 만료·폐기는 새 생성만 막고 기존 공간과 세션은 수명까지 유지한다. 보안상 강제 폐기는 운영자 runner의 별도 옵션으로, 해당 코드로 만든 공간과 세션을 즉시 무효화하고 DB·색인을 정리하며 사건을 남긴다.
14. **이어쓰기 쿠키(조건부).** 공간 생성 시 HttpOnly·Secure·SameSite=Lax 쿠키 `trial-resume`(공간 ID + 128비트 비밀, 수명 = 공간 수명)를 둔다. 서버는 비밀의 SHA-256만 저장한다. 세션이 끊긴 뒤 같은 코드를 다시 넣으면 쿠키 비밀이 일치할 때만 새 공간 대신 그 공간에 재접속한다. 재접속 때마다 세션 ID를 재발급하고(세션 고정 방지, Spring Security `changeSessionId`) 이어쓰기 비밀도 회전해 쿠키를 다시 내린다. 공간 초기화·만료·정리·강제 폐기 시 비밀을 무효화한다. 쿠키가 없거나 불일치면 새 공간을 만든다. 이것은 인증 계층 추가가 아니라 재입력의 결과를 같은 공간으로 이어 주는 편의 장치이며, 코드 자체의 검증은 항상 먼저 수행한다.
15. **한 코드로 여러 평가자.** 코드 입력마다 공간과 세션이 새로 만들어지므로 같은 코드를 쓰는 평가자끼리 DB·색인·실행 기록이 분리된다.
16. **요청 제한은 정상 체험을 방해하지 않는 수준으로 두고 시간 구간 실측으로 검증한다.** 코드 입력은 엄격하게(IP당 분당 5회, 코드당 분당 10회, 실패 5회 뒤 15분 잠금), 세션 내 요청은 넉넉하게(세션당 분당 120회, AI 호출 분당 20회·공간당 하루 300회, 공간별 변경 상한). 값은 설정이며 E2E에서 정상 시나리오의 **임의 60초 구간 최대 요청 수**가 제한의 절반 이하임을 확인하고, 정상 시나리오에서 429가 0회여야 한다. 429에는 `Retry-After`를 준다.
17. **감사.** 제어 DB: 코드 시도(IP 해시, 결과), 공간 생성·이어쓰기·역할 전환·초기화·만료·정리 사건, grant 발급·사용. 업무 DB: 기존 감사(Tool 호출, 준비안 실행, 사람 결정, 확인 기록)에 principal과 실제 수행 역할. 접근 로그는 principal, workspace, 경로, 상태, 소요 시간만 남기고 본문·토큰은 남기지 않는다.
18. **운영자 기능은 HTTP에 없다.** 코드 발급·폐기, 공간 목록·강제 정리, 템플릿 재구축은 runner 명령이다. 웹에서 관리자 권한을 얻는 경로가 없다.

## 근거

- DEVELOPMENT_RULES: API/Tool마다 사용자·서비스 권한과 담당 범위 검사, 클라이언트가 보낸 actor 불신, 최소 데이터, 감사 추적, fail-closed.
- ADR-011·012: 서비스 토큰 경계와 "기록은 사용 허가가 아니다". grant는 이 경계를 사용자 범위로 좁힌다.
- 사용자 요구: 업무 API 비공개, BOLA 차단, 토큰 노출 대비, 체험 기능 무제한과 체험자 격리, 반복 인증 없음.
- 대안 검토: (a) 서비스 토큰만 유지 → 유출 시 전 공문군 조회·임의 기록 가능, 거절. (b) AI 서비스에 사용자 신원을 넘겨 AI 서비스가 검사 → 권한 소유자가 둘, 거절. (c) 프록시 헤더로 신원 전달 → 헤더 위조 검증 필요, 거절. (d) workspace 열 + RLS 논리 격리 → 유일 제약·보호 함수 전면 재설계, 누락 시 누출, 거절. (e) 체험 공간별 컨테이너 묶음 → EC2 1대로 불가, 거절. (f) 체험 코드 뒤 추가 로그인 → 사용자 요구와 어긋남, 거절. (g) VPN·IP 허용 목록 → 평가자 접근 방식과 어긋남, 거절(운영자 서버 접근은 SSM).

## 검증 기준 (구현 Task의 AC에 그대로 넣는다)

- 세션 없는 행원·검수자 경로 전부 401. STAFF 활성 역할로 REVIEWER 경로 403, 역할 전환 뒤 200, 감사 행에 수행 역할.
- 사용자 A 세션으로 B의 상담 ID·준비안 ID·변경안 ID 접근 403 또는 404, 라우팅이 A의 DB를 벗어나지 않음.
- require-grant=true에서 서비스 토큰만으로 Tool·기록 401. grant 수용 기준 9항 전부. grant의 workspace를 바꾼 호출 403.
- 체험 공간 A의 승인 뒤 B의 적용 공문 조회는 검토 대기, `main`·템플릿의 사람 결정 행 수 0, A의 색인에만 문서.
- 코드 실패 5회 뒤 잠금, 만료·폐기 코드 401(공간 미생성, 시도 기록만), 강제 폐기 뒤 해당 세션 401과 DB·색인 삭제.
- 이어쓰기: 세션 만료 뒤 같은 브라우저 재입력은 같은 공간, 세션 ID와 비밀이 바뀜, 초기화 뒤 옛 쿠키 무효, 다른 브라우저는 새 공간.
- 정상 체험 E2E(코드 → 비교 → 시점 조회 → 변경안 생성·검증 → 승인 → 준비안 → 검색 → 확인 기록)에서 재인증 0회, 429 0회, grant 오류 0회. 임의 60초 구간 최대 요청 수 ≤ 제한의 50%.
- 브라우저 정적 자원과 응답 본문에 토큰·DB 이름 없음. AI 서비스·ES·PostgreSQL 외부 도달 불가.

## 결과

- 사용자 권한과 workspace는 Core가 세션과 grant로 정하고 AI 서비스·ES·DB는 그 결정을 따라갈 뿐 스스로 범위를 고르지 않는다.
- 체험자는 자기 공간에서 모든 업무를 실제 API와 DB로 수행하고, 그 결과는 다른 공간과 운영 데이터에 닿지 않는다.
- 운영 전환 시 form 로그인을 조직 인증(OIDC)으로 바꾸는 것은 인증 공급자 교체로 한정된다.

## 세부 설계 (TASK-017a·026·027에서 이 결정의 범위 안에서 정함)

- 표 구조, Flyway 위치(제어 DB 별도 history), 라우팅 DataSource와 풀 크기, provisioner 계정.
- 체험 공간 생성의 부분 실패 처리(DB 복제·색인 생성·세션 발급 순서, 보상 삭제, 동시 생성)와 요청 시 생성 vs 사전 생성 풀의 선택.
- grant와 업무 기록의 정합성 검증 항목, 제한값, 정리 작업 주기.
- 활성 역할 전환 경로와 화면 표시, 직무 분리 안내 문구.
