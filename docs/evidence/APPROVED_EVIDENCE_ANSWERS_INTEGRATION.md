# 승인 근거 AI 답변과 요청 기록 통합 검증

## 범위와 출처

- 기준선: main `0492490`. 분리 브랜치 `feat/approved-evidence-answers`, TASK-030.
- 기존 구현: `6e875e6`, `a17dc05`의 답변/기록 흐름과 `origin/feat/ai-eval-final`의 `1c542a5`에 있는 최신 답변 검사 모듈을 선별했다. Java 컨트롤러와 DB 검증은 V13 단계에서 필요한 부분만 반영했다.
- 실제 검색은 main의 기존 BM25 기본값과 BM25/vector/hybrid 선택 경로를 유지한다. 공통 JSON 검색 프로필과 후속 검색 조정, 공문 변경 비교 API, V14 이후 업무 기능은 포함하지 않았다.
- UI, 모델 가중치, 비밀값, 원본 snapshot과 대량 로그/캡처는 제외했다. 기존 브랜치와 과거 실행 기록은 보존했다.

## 실행 결과

아래는 커밋 전 상태의 로컬 검사 결과이다. Java 전체 통과 후 오류 응답 검사의 입력을 실제 승인 근거로 좁혔고 해당 연결 8건을 다시 통과했다. 최종 커밋 CI로 전체를 재확인한다. 실행 로그는 로컬 작업 공간에 두고 Git에는 요약만 기록한다.

| 검사 | 환경 및 명령 | 결과 |
|---|---|---|
| Python 전체 | Python 3.11 기존 AI venv, `PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -t .` | Python 233건 중 228 통과, 실패 0, skip 5 |
| Java 전체와 jar | Java 21, `TRUST_AGENT_REQUIRE_AI_INTEGRATION=1 ./gradlew :apps:core-service:test :apps:core-service:bootJar --offline --no-daemon -PaiServiceIntegration=true -x :apps:core-service:prepareAiServiceEnv` | 260건 중 257 통과, 실패 0, skip 3. jar 생성 성공 |

Java 로컬 실행은 기존 AI 검증 venv를 재사용해 환경 생성만 제외했다. 테스트 자체는 제외하지 않았다. CI는 기존 의존성 설치와 필수 연결 검증 경로를 사용한다. Python의 로컬 모의 HTTP 서버와 Docker 접근에는 실행 환경의 권한이 필요했다.

Python skip은 비공개 원문 파일이 없는 2건, 실제 임베딩 모델 경로를 지정하지 않은 3건이다. Java skip은 별도 플래그가 필요한 계측, 검색 평가, UI 브라우저 runner 3건이다. 답변 연결 검사는 건너뛰지 않았다. 실제 모델과 유료 호출은 실행하지 않았다.

## 자동 검증에서 확인한 대표 사례

`ConsultationAnswerIntegrationTest`는 실제 Spring, PostgreSQL, Elasticsearch, Python uvicorn을 사용한다. LLM은 `fake-echo` 정해진 응답기이다. 아래는 테스트가 실제로 확인한 상태/필드이며 실제 모델의 답변 품질 사례가 아니다.

| 입력 또는 상황 | 확인한 결과 | 사용자가 검토할 점 |
|---|---|---|
| 담당자의 “중도상환수수료율과 적용 조건을 확인해야 하나요?” | `ANSWERED`, 근거와 인용 존재, Core 공문명/원문 사용, 감사 상태 `ANSWERED`, 질문 원문 미저장 | 답변과 Core 근거가 연결되는가. 설명 검증과 고객 적용 확정을 구분하는가 |
| “이 기업 대출을 승인해도 되나요?” | `DECISION_DECLINED`, 모델 호출 0회, 설명 없음 | 규정 설명과 결정 위임을 왜 구분하는가 |
| 미승인 셀러론 공문군 질문 | `EVIDENCE_HOLD`, 근거/설명 없음 | 미승인 자료를 편의상 보여주지 않는가 |
| 질문에 합성 기업명 포함 | `QUESTION_CONTAINS_IDENTIFIER`, grant 추가 발급 없음 | 어떤 정보가 모델로 전달되는가 |
| 다른 담당자의 상담 건 요청 | HTTP 404 | 상담 건의 존재와 근거를 타 담당자에게 노출하지 않는가 |
| AI가 미승인 또는 다른 공문군 근거 ID 반환 | `CORE_RECHECK_FAILED`, 설명 제외 | AI의 성공 주장보다 Core 상태를 우선하는가 |
| AI가 성공 상태지만 근거/인용이 비거나 답변 구조가 깨짐 | `ANSWER_HOLD`, 설명 없음, 보류 상태 기록 | 성공 상태만 믿지 않는가 |
| AI 연결 실패, 잘못된 JSON/상태 | `AI_UNAVAILABLE`, 설명 없음, 요청 이력 1건 | 실패를 정상 답변으로 표시하지 않는가 |

Python RAG 검사에서는 실제 모델 대신 정상/오류 응답을 넣어 없는 인용구, 근거 밖 수치/날짜/상품 범위, 근거 없는 변경 이력과 모델 오류를 차단하는지 확인했다. HTTP 검사는 인증 실패 시 검색 미호출, grant 전달, 내부 `_eval` 초안의 응답 제외를 확인한다.

## 통합 중 발견과 보완

- 최신 RAG 테스트가 운영 모드에서 평가 기록 설정을 거부하도록 요구했으나, main의 설정 검사에는 해당 항목이 없어 첫 실행이 실패했다. 관련 기동 거부 검사만 선별해 반영했으며 검색 프로필 변경은 끌어오지 않았다.
- Core 재확인이 근거 ID 포함 여부만 검사하면 빈 근거/인용의 성공 응답이 통과할 수 있었다. 성공 답변의 필수 구조와 근거/인용 존재를 검사하고 실제 승인 근거를 사용한 오류 응답 회귀 검사를 추가했다.
- 로컬 모의 모델 서버 테스트 종료 때 열린 소켓 경고가 있어 종료 후 소켓을 닫도록 수정했다.
- 제한된 실행 환경의 포트 바인딩 거부는 skip으로 숨기지 않고, 권한이 있는 환경에서 같은 전체 Python 검사를 다시 실행했다.

## 검증 한계와 사용자 검토

- 정해진 응답기를 사용한 연결 검사는 모델이 한국어 질문에 정확히 답하는지 증명하지 않는다. 실제 모델 검색/답변 비교와 사람의 근거 대조는 후속이다.
- 생성과 추가 검증에 같은 모델을 쓰면 같은 오류를 놓칠 수 있다. 문장 인용과 수치 등 코드 검사도 의미 전체를 보장하지 않으며 직원 원문 확인이 필요하다.
- 요청 감사는 상태, 해시, 근거 ID와 사용량을 남기는 기능이다. 질문/설명 원문을 저장하지 않아 그 기록만으로 당시 문장 전체를 복원할 수 없다.
- Core 재확인은 조회 시점의 승인 상태를 확인한다. 이후 철회를 막거나 대출 승인/고객별 적용을 확정하지 않는다.
- 사용자는 대표 사례를 원문과 대조하고, 입력 → 승인 근거 검색 → 생성/검사 → Core 재확인 → 요청 기록의 흐름, 보류 이유와 남은 한계를 설명한 뒤 병합 여부를 결정한다. 인간 검수와 Explainability Gate는 대기이다.
